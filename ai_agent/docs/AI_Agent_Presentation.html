The problem we solve

Students and staff ask the registrar the same questions all semester: course details, policies, eligibility, enrollment, transcripts. Every answer lives in a database — but someone has to dig it out, table by table.

Our agent answers from the real database, runs the checks deterministically, and executes enrollment safely — behind a human confirmation gate.

LLM never writes facts

It only classifies intent and extracts entities as JSON. Every fact in a reply comes from a tool result.

Deterministic below the LLM

Routing, validation, tools, and phrasing are plain code — testable without a model.

Swappable model

Provider and model are environment variables; OpenAI/Anthropic are optional fallbacks.

4 / 10

Structured grounding — why we didn't use RAG

Our knowledge source

  • SQLite — the existing UMS schema: students, courses, prerequisites, sections, enrollments, grades, accounts
  • policies.json — policy text with exact values (fees, GPA thresholds, deadlines)
  • Accessed only through deterministic typed tools — exact SQL, no similarity search
  • Precise, reproducible, auditable — same question, same values

Why RAG is the wrong tool here

The domain is small, structured, enumerable. Embeddings add infrastructure and nondeterminism — and a retrieved paragraph can't be joined, summed, or re-validated like a row.

When RAG would pay off

Large unstructured corpora: a 400-page academic handbook, accreditation documents, free-text advising notes. Even then it complements the tools — exact values stay structured.

An explicit state machine, not a free agent

Intent→ Gather→ Validate→ Analyze→ Confirm→ Execute→ Report

Fallback  ← low confidence · unsupported · too many iterations

Confidence threshold

Intent below 0.4 → deterministic fallback: state the limitation, never invent an answer.

Confirmation gate

The only state-changing tool previews (confirm=false) until the user says yes — enforced by graph structure, unbypassable by prompts.

Stopping rules

Max 6 iterations per turn; yes/no with nothing pending routes to fallback.

Human handoff

"Talk to a human" matches a regex — works even if the LLM is down — and files a traceable HANDOFF ticket.

Every intent, tool call, validation failure, and fallback → agent_logs audit table.

Three kinds of memory

REQUIRED

Short-term

The conversation: messages, the user's name and role — so "my GPA" resolves to the right student without restating who they are.

REQUIRED

Working

Explicit task state — current intent, collected info, missing fields, pending confirmation, latest tool result, workflow state. Rendered live in the side panel.

BONUS

Long-term

Per-user preferences persisted in SQLite across separate sessions.

Seen in the demo: "What is my GPA summary?" → the agent resolves the student from session memory; "And my transcript?" → the identifier carries over from the previous turn.
